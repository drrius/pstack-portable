### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.** For "land the stack", "ship it", "drain the stack", or the second half of a stack that **Babysit** already drove to green.

This is the half after `playbooks/babysit.md`. Babysit makes a stack mergeable. Shipping decides what is actually safe to merge, then drains it one PR at a time. Green is not safe, and the gap between those two words is where this playbook lives.

1. **Verify every PR independently before merging anything.** One `verify` worker per PR, not batched, each exercising the real surface through the host's browser, desktop, CLI, or TUI control capability against parent versus head. Each returns `PASS`, `PASS+NOTES` or `FAIL` plus review provenance; when the forge and authorization allow, record that verdict on its own PR so it outlives the chat. Safe means a verdict from a fresh-context worker that did not write the code. If delegation is unavailable, stop before merge and request the exact independent manual verification rather than self-certifying. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable, because merging it would pull the gap in underneath it. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that the verdicts still describe the code.** A rebase rewrites every SHA above it and silently invalidates every verdict without touching a single check. Compare `git patch-id` at the verdict SHA against the current head before trusting an older verdict, and re-verify anything that actually drifted. Twenty-one verdicts went stale this way in one run with no signal at all.
4. **You are the sequencer, so merge one PR at a time from the bottom.** Nothing queues these merges for you. Merge the lowest verified PR into trunk through the repository's forge (the host contract's Source forge section), confirm from the forge that it actually merged, and only then look at the one above it.
   ```bash
   gh pr merge <n> --squash
   ```
   On Azure DevOps: `az repos pr update --id <n> --status completed --squash true`.
5. **Never arm auto-merge on a stack — GitHub auto-merge or Azure DevOps auto-complete alike.** Only the root targets protected trunk. Every child targets its unprotected parent branch and already reads `CLEAN`, so GitHub would merge children into parents immediately and collapse the stack into itself. Sequencing is the whole job of this playbook, and auto-merge takes it away from you. If a previous agent armed it, disarm it (GitHub: `gh pr merge <n> --disable-auto`; Azure DevOps: clear auto-complete on the PR) and confirm the field is back off.
6. **Retarget the next PR onto trunk before you touch its content.** Each merge orphans the base of the PR above it. Retarget through the forge (GitHub: `gh pr edit <n> --base <trunk>`; Azure DevOps: Change target branch on the PR, via the web UI or the pull request update REST API), then rebase the branch onto trunk and push it. The rebase rewrites every SHA above it and voids the verdicts pinned at the old SHAs, so re-apply the patch-id rule in step 3 and re-verify anything that actually drifted.
7. **Re-resolve the frontier after every merge, and touch nothing above the PR you are landing.** `orch frontier set` walks the forge's own base refs, so it reads the retargeting you just did rather than stale local metadata. No speculative pushes, no rebasing the whole chain at once, and no force-push from inside the drain. Independent work gets re-parented onto trunk and shipped on its own.
8. **Watch each merge, do not batch them.** Hold between merges through the host's wait/wake mechanism, re-armed after any verdict you act on, until the ceiling lands. Report each merge and the new ceiling. If a merge stalls, diagnose before mutating, because a stalled merge and a broken stack look identical from the outside.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1, not a judgment call you make at 3am.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you merged and how you confirmed it, what landed, and what the next gap needs.
